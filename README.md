# 插件管家 · dsh-plugin-curator

每天根据你在 DeepSeek Harness 里的真实工作内容，做三件事：

1. **推荐**：从五个渠道发现插件 → 去重 → 按「你最近 7 天的工具调用 + 工作区」打分 → **只把通过校验的条目摆出来**；点「启用」即通过官方 `pluginManager` 安装（官方内置但未启用的，只做启用，不下载）。
2. **优化**：对已装插件给出可执行建议——可升级版本、近期高频（值得调参）、权限偏宽、已启用但无调整。
3. **清理**：连续 `idleDays` 天没有可关联调用的插件进入「闲置」列表，可一键卸载或延后 30 天再提醒。

入口有两个（同一份数据）：**左侧边栏 →「插件管家」**（主入口，整页），以及 **设置 → 内置插件 → 插件管家**（页签）。每日存档写入 `$DSH_HOME/plugin-curator/reports/YYYY-MM-DD.md`。

## 每条推荐都自带三件事

面板上每一条都写清楚，不需要你去猜：

1. **为什么** —— 采纳度（月下载/星标）、维护信号（最近提交、半年未更新、issue 积压）、与你工作画像的匹配、以及**补的是哪个缺口**（会引用你的原话）；
2. **怎么装** —— 面板按钮一键装；旁边给出等价命令 `dsh plugin add <spec>`，方便你在终端或别的 profile 里复现；
3. **怎么用** —— 按类别给出具体动作（记忆类：启用后初始化记忆库；UI 类：刷新页面；定时类：配置一次计划）。

建议删除时同样给理由：`连续 N 天没有关联调用（最近一次 YYYY-MM-DD）`，而不是只说"闲置"。

## 界面

侧边栏整页 + 设置页签共用一套版式：顶部标题与刷新、四块指标、今日变化、能力重叠、需求缺口、推荐、已装、闲置、模型、数据源。

- 悬停/按下/聚焦态由一个注入的样式表统一提供，按钮与输入框都有过渡；
- 安装命令可一键复制；操作结果以底部浮层提示，不打断阅读；
- 窄屏自动降为两列指标。

模型卡支持：供应商、模型（图片能力自动标注）、**图片理解开关**、**推理强度**、每天次数、**测试连接**（显示耗时或失败原因）。

## 侧边栏面板

在 `sidebar.panellist` 注册一行、在 `main` 注册一个面板页（与 `dshmarket` 用的是同一套公开插槽）：

- 整页展示：缺口 / 推荐（含为什么·怎么装·怎么用）/ 已装 / 闲置 / 数据源覆盖 / 模型设置；
- 已装区每个插件都有开关（启用/停用）与卸载（受保护包除外）；
- 每个已装插件显示**关联调用数、最近使用日期、主要工具**（如 `ops_bash 276`）。

宿主没有该插槽时自动跳过，只保留设置页签，不会连带弄坏已注册的页签。

## 按工具归因失败

`tool/call` 与 `tool/result` 按 `callId` 配对（缺失时按到达顺序回退），失败归到具体工具：

```
run_code   456 次 / 15 败 (3%)
ops_bash    36 次 /  1 败 (3%)
web_fetch    5 次 /  1 败 (20%)
```

某个工具「调用 ≥10 次且失败率 ≥20%」时，生成一条指名道姓的缺口（"工具 X 经常失败"），并按该工具的能力域（read → 文件/检索）去匹配候选。

> 注意：早期版本用正则扫文本里的 "error" 统计，把正常输出里的字样也算成失败，报出过 22% 的假数据；按 `data.error` 精确计数后真实值约 3%。

## AI 发现：你没提、也不属于"出厂缺口"的好插件

开启模型后，每次分析会把「已装插件 + 工作画像 + 工具失败统计 + 前 40 个候选（名称/分类/描述/下载/星标）」交给模型，要求它输出：

- `needs`：规则没覆盖到的需求；
- `picks`：最多 3 个**能实质提升效率**的候选，并给出具体理由。

picks 会按**精确包名**回到注册表校验（必须声明 `dsh` 字段），通过后置顶并标「AI 推荐」。这样即使某个插件既不在你的提问里、也不属于任何出厂缺口，只要模型判断它有用，就会被摆到面前。

实测：模型自行挑出了 `@deepseek-ai/dsh-experimental-session-search`（官方内置但默认关闭的会话检索）与 `@michengai/dsh-archive-manager`，两者都进入了当天的列表。

## 行为信号：工具报错率也进打分

除了"你说了什么"，还看"工具做得怎么样"：从会话日志统计 `tool/result` 的次数与报错数（`error|failed|ENOENT|ECONN|EPERM|timeout`）。当调用量 ≥20 且错误率 ≥15% 时，生成一个 `tooling`（工具调用可靠性）缺口，并只对**描述命中测试/校验/调试/重试/可观测**的候选加分——不会把所有 tools 类插件都抬上来。

实测：8 个会话 583 次工具调用、127 次报错（22%），当天就出现了这个缺口。

## 能力升级槽：你没提，但系统本来就没有

除了从提问里挖缺口，还有一份**固定能力清单**，Harness 出厂就不具备：

| 能力 | 判定覆盖的关键词 | 举例 |
|---|---|---|
| 会话记忆 | 记忆/memory/recall | 跨会话长期记忆 |
| 自进化 | 自进化/进化/反思/经验沉淀 | 把做过的事沉淀成经验 |
| 会话管理 | 会话检索/归档 | 历史会话搜索与归档 |
| 自动化 | 定时/自动化/schedule | 真正的定时任务 |

只要没有任何已装插件覆盖某一类，这类里得分最高的候选会拿到一个**保底槽位**，标「能力升级」并说明理由——不依赖你有没有提过。

实测这一轮（你从没直接要过"自进化"）：`dsh-continual-evolve`、`open-dream-rsi` 被自动顶进推荐，理由是「Harness 出厂不带自进化与经验沉淀」。

同一缺口最多占 2 条推荐，避免一条缺口吞掉整个列表。

## 出厂缺口：Harness 没有的能力，天天提醒

有些能力 Harness 本身不提供——跨会话记忆、真正的定时自动化。这类不是"你想要"，而是"你没有"，所以作为**常驻缺口**参与排序，直到装了能覆盖它的插件为止：

- 记忆（`memory` 分类）
- 自动化（`workflow` 分类）

卡片上标「出厂缺口」，与从你提问里挖出来的「需求缺口」区分开。用配置 `baselineGaps: false` 可关。

## 采纳度闸门：不是「存在」就值得推荐

实测社区注册表 6,565 条里，**3,403 条（52%）月下载为 0**，中位数就是 0；星标中位数 1，31% 为 0。所以"能装"和"值得装"是两件事。

| 档位 | 判定 | 处置 |
|---|---|---|
| `proven` | 月下载 ≥ `minDownloads`(100) 或 星标 ≥ `minStars`(5) | 正常参与排序 |
| `new` | 发布 ≤ `newPluginDays`(14) 天、还没有数据 | 最多 `emergingMax`(2) 条，带「新发现」标记，不参与自动安装 |
| `unused` | 又老又没人用 | **不进入推荐**，只计入覆盖统计（面板显示「低信号剔除」） |

新插件不会漏：每次刷新都会把新出现的 id 写进 `catalog.json`（含首次出现日与版本），面板显示「近 7 天更新」的数量。第一次运行是基线，不会把全量当成"新闻"。

## 静默多次分析 + 可选模型

- **节奏**：`runsPerDay`（默认 3）按间隔跑，不再固定早上 9 点；关掉窗口也在后台跑，报告随取随看。
- **数据**：读你最近 14 天、最多 8 个会话里的 user/message；同时统计 assistant/message 轮数、tool/result 次数与**报错率**。助手正文不参与缺口判定（它会把我自己说的话放大成需求），但轮数与错误率会作为**行为信号**进入分析摘要。
- **模型（可选，默认关）**：面板里选供应商 + 模型，列表来自 Harness 已配置的 `ctx.llm`（与 设置 → 模型 是同一份配置），设置存在 `plugin-curator/settings.json`。每次跑只发送**压缩摘要**（缺口、错误率、已装插件名、前 40 个候选的描述），不发送完整对话。

## 对话找插件

面板第一个页签是对话框：用中文描述需求 → 本地在 6,800+ 条候选里做关键词预筛（中英文分词、标题加权、下载量微调）→ 把前 24 条交给所选模型 → 返回一段中文回答和最多 3 个候选，每个都能直接安装。

- 候选只来自已同步的索引，模型不能凭空编包名；
- 索引落盘在 `plugin-curator/index.json`（约 3.4 MB），重启后对话框照样可用；
- 模型不可用时退化为纯关键词结果，并说明原因。

## 能力重叠面板

洞察页的「能力重叠」按能力分组列出覆盖同一类功能的已装插件，每组给出：

- 组名与该组插件数
- 每个插件的描述、版本、调用次数、工具数、最近使用时间、闲置天数
- 「主力」标记（该组内调用次数最多者），方便判断谁在真干活
- 每个插件后面直接给「卸载」按钮（两次点击确认），不用跳回已装页

安装成功后立即重算重叠：新插件若与已装插件撞能力，会立刻出现在该面板，并在安装提示里告知撞了几组。

## 卡片上的市场信号

每张推荐卡片显示一行数据，用来判断"这个插件有没有人在用"：

| 指标 | 来源 | 说明 |
|---|---|---|
| ↓ 月下载 | npm 搜索接口的 monthly downloads | **npm 不公布安装量**，这是最接近的公开数据 |
| ★ 星标 | GitHub stars | 关注度，不等于质量 |
| ⑂ 派生 | GitHub forks | 有人真的拿去改，通常比星标更硬 |
| 热度超过 N% | 由候选池下载量分布算出的百分位 | "超过 88%" = 比 88% 的候选下载量高 |
| 更新 | 最近提交/发布时间 | 维护活跃度 |

没有市场数据的条目（官方内置包、刚发布的仓库）显示「暂无市场数据」，而不是把 0 当成差。

## 缺口直接挂候选

每个缺口下方给出最多 2 个能补它的候选（可一键启用）；没有匹配时明确显示「暂无，下次重试」。

## 中文文案

- 注册表自带的中文描述优先于英文；
- 没有中文的候选，由所选模型批量翻译（每批 6 条，按包名缓存在 `state.translations`，不重复计费）；
- 模型关闭时回退英文原文。

## 需求缺口：先想「你缺什么」，再想「装什么」

单纯按关键词和下载量排序，只会推荐「热门」，不会推荐「你需要的」。所以面板顶部多了一张**需求缺口**卡片：

1. 用 `ctx.sessionQuery` 读最近 `intentDays` 天、最多 `intentSessions` 个会话里的 **user/message**（只读你打的字，不读助手的话——否则每个话题都会被自己的回答放大成需求）；
2. 先把 Harness 注入的运行时上下文和 `<system-reminder>` 剥掉，再跑 12 条能力意图规则（记忆、自动化、检索、文档、视觉、Git、通知、数据、语音、笔记、多智能体、界面）；
3. 命中 `intentMinHits` 次、且**没有已装插件覆盖**，才算一个缺口；
4. 候选插件只有在「分类命中 且 描述命中」时加分 +12，并标注「补缺口」。

实测：问过两次「Harness 有没有会话记忆自进化」之后，面板立刻把 `dsh-memory`、`dsh-auto-memory`、`memsearch` 提到前排，并显示原话作为证据。

缺口是**推断**，不是事实：它只说明「你在要这类能力，而当前没有插件覆盖」，不代表某个插件真的解决了它。所以证据原话会和推荐一起摆出来，供你判断。

## 数据源与覆盖

「发现要宽，展示要窄」：五个渠道负责宽，校验负责窄。

| 渠道 | 抓取方式 | 实测规模（2026-10-23） | 硬限制 |
|---|---|---|---|
| 官方内置 | `pluginManager.listBundles()` 里 `availability=installation` 且未启用的行 | 12 | 无（本地，零网络） |
| 社区注册表 | `awesome-dsh-plugin.com/plugins.json` | 6,565 条 | 只有一个社区索引，是单点 |
| npm | `keywords:dsh-plugin` + `keywords:deepseek-harness`，每页 250 分页 | 每查询 ~5,500，去重后贡献 ~4,300 | 搜索 API 超过约 5,000 条会回卷到第一页，必须分查询绕开；突发请求会 429 |
| GitHub | `topic:dsh-plugin`、`topic:deepseek-harness`，排序取最新 | 264（2×2 页×100） | 该 topic 有 21,812 个仓库，大量是"顺手打标签"的非插件；未认证 60 次/小时 |
| 自定义市场索引 | `marketIndexes` 里的 format 1 索引 | 0（默认不配） | DSH 官方市场**默认不配置任何索引**，Discover 需要你先加 URL |

合并去重后，本次实测 **10,902** 个候选。

### 校验：不是"搜到就推荐"

候选在进入列表前要证明自己是**真的可安装插件**：

- npm 包 → 读 packument，`versions[latest].dsh` 必须含 `bundle` 或 `client`；
- Git 仓库 → 读 `raw.githubusercontent.com/<owner>/<repo>/HEAD/package.json`，`dsh` 字段同样判定；
- 官方内置 → 由构造保证。

只校验前 `validateTop`（默认 40）条，兼顾覆盖面与请求量。本次实测：40 条里剔除 1 条、留 39 条；另一轮剔除 6 条——被剔除的是带 `dsh-plugin` 关键词但没声明 `dsh` 字段的普通 npm 包。

页签底部的「数据源覆盖」卡片会逐条列出：渠道、抓取量 / 该渠道总量、去重后候选、已校验、已剔除、实际展示。**覆盖不足会显示出来，而不是藏起来。**

## 配置

在 profile 的 `cordis.patch.yml` 里覆盖 `plugin-curator` 这一行：

```yaml
- id: plugin-curator
  name: dsh-plugin-curator
  config:
    dailyHour: 9              # 每天几点后重新生成
    idleDays: 30              # 多少天没用算闲置
    maxRecommendations: 8     # 一天最多几条推荐
    autoInstall: false        # 关：只推荐，点了才装
    autoInstallMinScore: 85
    autoInstallMax: 2
    validateTop: 40           # 校验多少条候选
    npmSearch: true
    npmQueries:               # 多查询绕开 npm 的 5000 条回卷
      - keywords:dsh-plugin
      - keywords:deepseek-harness
    npmPages: 24              # 每个查询翻多少页（250/页）
    npmDelayMs: 300           # 页间隔，防 429
    githubSearch: true
    githubPages: 2
    githubToken: ''           # 未认证只有 60 次/小时
    sources:
      - https://awesome-dsh-plugin.com/plugins.json
    marketIndexes: []         # format 1 索引 URL，可多个
```

## 边界

- 安装 / 卸载只由你点按钮触发；Agent 侧的 `plugin_curator_status` 工具是只读的。
- 路由只接受 loopback Host，拒绝 `Sec-Fetch-Site: cross-site` 与跨源 `Origin`。
- 「关联调用」是按插件名 / 行 id 与工具名做最长词匹配的**估算**。
- 首次生成约 90 秒（~44 个 npm 分页 + 40 次校验）；之后每天一次，错过就在下次启动补跑。
- 打分是启发式：冷启动（没有历史用量）时更依赖下载量、星标与新鲜度，用几天后才会贴合你的工作内容。
